### 1. Executive Summary & Strategic Problem Context

Enterprise software landscapes distribute cryptographic primitives across source repositories, build pipelines, stripped native binaries, OCI container images, cloud Key Management Services (KMS), and live TLS endpoints. This lack of centralized visibility prevents organizations from establishing an auditable inventory of deployed algorithms, key lengths, and trust paths. In the face of impending Cryptographically Relevant Quantum Computers (CRQCs) capable of breaking classical public-key cryptography (RSA, ECC, Finite-Field Diffie-Hellman) via Shor’s algorithm, unmonitored cryptography introduces immediate exposure to retroactive **"Harvest Now, Decrypt Later"** attacks.

The **Enterprise Cryptographic Discovery & Analysis Tool (ECDAT)** bridges the critical research gap in software assurance. Rather than operating as a conventional passive scanner, ECDAT is designed as a **cryptographic intelligence and decision-support platform**. It fuses multi-modal evidence across the full technology stack into a unified cryptographic asset graph, executes probabilistic quantum risk simulations based on Mosca’s inequality, enforces policy drift gates in CI/CD pipelines, and outputs optimized, risk-prioritized Post-Quantum Cryptography (PQC) migration roadmaps.

### 2. Multi-Modal Evidence Fusion Architecture

A single scanning modality cannot cover heterogeneous cloud and software environments. ECDAT integrates four specialized discovery engines into a unified evidence fusion pipeline:

#### A. Static Source Code & Rule-Based AST Scanner
Operating on the principles established by the **Crypistry/Crypsy** framework, source code analysis uses Abstract Syntax Tree (AST) parsing, regex matching, and manifest parsing. Inputs are categorized into three orthogonal discovery classes:
* **Crypto-Material:** Value-centric assets such as private keys, symmetric keys, tokens, seeds, and entropy blobs.
* **Crypto-Artifacts:** Structure-centric objects containing security metadata, such as X.509 certificates, PKCS#12 keystores, and trust stores.
* **Crypto-Invocations:** Context-centric usage points, including cryptographic API calls, cipher suite parameters, and dependency declarations.

In empirical benchmark evaluations (*Cryben*), static rule-based discovery achieved an overall \\(F_1\\) score of \\(0.75\\) (\\(F_1 = 0.94\\) for Crypto-Material, \\(F_1 = 0.92\\) for Go AST invocations) and an assessment recall of \\(0.91\\) when annotating CWE weaknesses (e.g., CWE-327, CWE-338) and CVE vulnerabilities.

#### B. Stripped Binary Discovery & Lineage Attribution (*Kestrel Engine*)
Name-based and symbol-based binary scanners fail completely when binaries are stripped, statically linked, or compiler-optimized. ECDAT incorporates the **Kestrel** detection methodology, which targets invariant mathematical fingerprints embedded in read-only data sections (`.rodata`, `.noptrdata`). 

Lattice-based PQC schemes (**ML-KEM** and **ML-DSA**) perform polynomial arithmetic using the Number-Theoretic Transform (NTT). The NTT requires precomputed tables of powers of a primitive root of unity \\(\zeta\\) modulo prime \\(q\\) (\\(\zeta\\)-tables):
* **ML-KEM (FIPS 203):** \\(q = 3329\\), \\(\zeta = 17\\), length-128 table stored in plain or Montgomery form (\\(\zeta_{\text{mont}}[i] = \zeta^{\text{BitRev}_7(i)} \cdot 2^{16} \bmod 3329\\)).
* **ML-DSA (FIPS 204):** \\(q = 8380417\\), length-256 table.

```
Baseline Source Binary                After Stripping, -O2, & Static Link
┌─────────────────────────┐           ┌─────────────────────────┐
│ .text: Function Symbols │  ─────►   │ .text: Rewritten Code   │ (Symbols Erased)
├─────────────────────────┤           ├─────────────────────────┤
│ .rodata: NTT $\zeta$-Table│  ─────►   │ .rodata: NTT $\zeta$-Table│ (Byte-for-Byte Identical)
└─────────────────────────┘           └─────────────────────────┘
```

Because these mathematical tables constitute read-only data essential for algorithmic correctness, compiler optimization and symbol stripping cannot alter them. The detector uses windowed normalization (reducing plain, signed-Montgomery, and unsigned-Montgomery representations to canonical residues) and multiset threshold scoring. Across 6,224 production Linux binaries, this technique achieved **recall of \\(128/128\\) with zero false positives**.

Furthermore, ECDAT uses the total twiddle-byte count to attribute binary detections directly to source lineages:
* **1 Table (256 Bytes):** C-reference / `liboqs` / `PQClean` lineage (Montgomery signed).
* **2 Tables (512 Bytes):** Specification-derived lineage (Go standard library `crypto/mlkem`, `RustCrypto` crate).
* **3 Tables (768 Bytes):** `BoringSSL` lineage (includes explicit inverse tables).

#### C. OCI Container & Image Discovery
Utilizing containerized orchestration patterns (derived from **BF-CBOM** and **QRCS-CBOM**), ECDAT streams OCI image tarballs layer-by-layer. It unpacks file systems safely, parses Linux trust stores (`/etc/ssl/certs/`), inspects embedded web server configurations (`nginx`, `apache`), and extracts compiled binaries for inspection. File duplication across layers is resolved by deduplicating assets on canonical algorithm parameters, public key fingerprints, and certificate distinguished names.

#### D. Live Endpoint Probing & Cloud KMS Integration
ECDAT includes active collectors for live TLS/QUIC handshakes and cloud infrastructure:
* **TLS/QUIC Probes:** Connects to endpoints to negotiate cipher suites, extract leaf/intermediate X.509 certificate chains, and detect quantum-vulnerable key exchanges.
* **Cloud KMS Collectors:** Interfaces with AWS KMS/ACM, GCP Cloud KMS, and Azure Key Vault via APIs to map customer-managed keys, asymmetric wrapping pairs, and certificate lifecycles.

### 3. Standardized Asset Classification & xBOM Ecosystem

To ensure interoperability with regulatory frameworks (e.g., EU Cyber Resilience Act, DORA, NIS2, US CNSA 2.0), ECDAT normalizes all discovered assets into **OWASP CycloneDX v1.6/v1.7 (ECMA-424)** standards and the **QRCS `.qcbom.json`** project model.

#### Asset Schema Mapping (CycloneDX `crypto-asset`)

| Asset Category | Detailed Subcomponents & Metadata Properties | Standard Schema & Lifecycle Mapping |
| :--- | :--- | :--- |
| **Algorithms** | Primitive (KEM, MAC, Signature, Hash), Family (AES, RSA, ML-KEM, SLH-DSA), Variant, Key/Parameter sizes, Classical Security Level (bits), NIST Quantum Security Level (1–5). | CycloneDX `crypto-asset` (subtype: `algorithm`). |
| **Protocols** | Family (TLS, SSH, IPsec, QUIC), Version (e.g., TLS 1.3), Cipher Suites, IKEv2 Transforms, Handshake State. | CycloneDX `crypto-asset` (subtype: `protocol`). |
| **Certificates** | Subject/Issuer Distinguished Names, Serial Number, Validity Dates (`notValidBefore`, `notValidAfter`), Key Usage extensions, Signature Algorithm. | CycloneDX `crypto-asset` (subtype: `certificate`). |
| **Crypto Material** | Private/Public Keys, Secrets, Tokens, Passwords, Key Size, Storage Backing (HSM, TPM, Software), NIST SP 800-57 Lifecycle State (active, suspended, compromised). | CycloneDX `crypto-asset` (subtype: `material`). |

#### Full-Stack xBOM Composition
ECDAT links cryptographic assets across all operational layers using CycloneDX **BOM-Link** (IANA URN namespace):
1. **Software BOM (SBOM):** Maps software dependencies (e.g., `OpenSSL`, `liboqs`, `golang.org/x/crypto`).
2. **Operations BOM (OBOM):** Links runtime configuration files (e.g., OpenSSL `DEFAULT_GROUPS`, nginx `ssl_ciphers`) to actual negotiated algorithms to detect configuration drift.
3. **Hardware BOM (HBOM):** Captures hardware security modules (HSMs), TPMs, and cryptographic coprocessors, recording FIPS 140-3 certification levels.
4. **SaaS BOM (SaaSBOM):** Maps cloud KMS key management endpoints, CA services, and external crypto APIs.

### 4. Quantitative Quantum Risk Engine

Deterministic Q-day planning (e.g., assuming a fixed Q-day of 2035) fails to capture tail uncertainty. ECDAT implements a **two-layer risk model** combining probabilistic timing gates with cloud-aware contextual scoring:

#### Layer 1: Probabilistic Mosca Timing Gate (\\(X + Y > Z\\))
Mosca's inequality states that if data confidentiality lifetime (\\(X\\)) plus migration duration (\\(Y\\)) exceeds the time until a CRQC exists (\\(Z\\)), data is compromised:

\\[\text{Mosca Condition: } X + Y > Z\\]

ECDAT executes a **Monte Carlo simulation** (\\(N = 200,000\\) iterations) parameterized by expert-elicitation cumulative probability distributions for Q-day (\\(T_q\\)) from the Global Risk Institute (GRI):
* \\(T_s\\): Migration start year.
* \\(Y\\): Migration duration (\\(T_c = T_s + Y\\)).
* \\(X\\): Data confidentiality shelf-life.

For each iteration \\(i\\), the exposed fraction \\(f\\) of the confidentiality window \\([T_q - X, T_q]\\) is computed as:

\\[f(T_q; T_s, X, Y) = \min\left(1, \max\left(0, \frac{\min(T_q, T_c) - (T_q - X)}{X}\right)\right)\\]

The model outputs two core decision metrics:
1. \\(P(f > 0)\\): Probability that any portion of sensitive data is exposed prior to migration completion.
2. \\(E[f]\\): Expected exposed fraction of the data confidentiality window.

| Strategy | Start Year (\\(T_s\\)) | Completion Year (\\(T_c\\)) | Exposure Probability \\(P(f > 0)\\) | Expected Exposed Fraction \\(E[f]\\) | Strategic Impact |
| :--- | :---: | :---: | :---: | :---: | :--- |
| **Early Start** | **2026** | 2032 | **0.59** | **0.37** | Baseline exposure; maximum risk reduction. |
| **Moderate Start** | **2028** | 2034 | **0.67** | **0.45** | Exposure grows by +8% probability. |
| **Delayed Start** | **2030** | 2036 | **0.73** | **0.54** | **Exposes over half (54%) of the data window**. |
| **Reactive Start** | **2032** | 2038 | **0.75** | **0.62** | Severe risk; critical regulatory non-compliance. |

#### Layer 2: Cloud Contextual Risk Engine
Layer 2 overlays the timing gate with threat mechanics and system reachability:
1. **Retroactive Confidentiality Loss ("Harvest Now, Decrypt Later"):** Applies to asymmetric key exchange/agreement primitives (RSA, ECDH) used in TLS, VPNs, and KMS envelope encryption. Evaluated against \\(X\\); high \\(X\\) values demand immediate prioritization.
2. **Forward Integrity & Authentication Loss:** Applies to digital signatures (RSA, ECDSA) in PKI, mTLS, code signing, and CI/CD pipelines. Evaluated as active forgery and impersonation risks once a CRQC exists.
3. **Contextual Drivers:** Scores reachability (internet-facing ingress vs. internal service mesh), blast radius, business criticality, and cryptographic agility.

### 5. Actionable PQC/Hybrid Recommendation & Migration Optimization

ECDAT provides direct, actionable remediation paths for every identified vulnerable asset:

#### A. Algorithmic Replacement Mapping
* **Key Encapsulation Mechanisms (KEM):** Replace RSA/ECDH with **NIST FIPS 203 (ML-KEM-512 / ML-KEM-768 / ML-KEM-1024)**.
* **Digital Signatures:** Replace RSA/ECDSA with **NIST FIPS 204 (ML-DSA-44 / ML-DSA-65 / ML-DSA-87)** or **NIST FIPS 205 (SLH-DSA)** for stateless hash-based protection.
* **Symmetric Primitives:** Upgrade AES-128 to **AES-256** and SHA-256 to **SHA-384 / SHA-512** to maintain security margins against Grover's algorithm speedups.

#### B. Hybrid Deployment Architecture
To prevent single-point-of-failure risks during early PQC deployment, ECDAT recommends hybrid key exchange (combining classical and quantum-resistant primitives) per **IETF RFC 10024 / draft-ietf-tls-hybrid-design**:
* Combine **X25519 + ML-KEM-768** for TLS 1.3 / QUIC handshakes.
* Ensures security as long as at least one constituent scheme remains unbroken.

#### C. Crypto-Agility Scoring & CI/CD Policy Gates
1. **Agility Scoring:** Evaluates replaceability—High agility for cloud KMS rotated via API; Medium for parameters configurable via runtime config; Low for hardcoded source or compiled code.
2. **CI/CD Drift Enforcement:** Evaluates Common Expression Language (**CEL**) policies during builds to block newly introduced weak or quantum-vulnerable algorithms:
